# 鮮度 — このKBが美術史のKBと違う一点

美術史の事実は固まる。新印象派の始点1886年は、一度一次資料で確定すれば永久に1886年で、
`verified` は上がったら下がらない。

マーケティングの事実は腐る。「ショート動画の利用率」「主要チャネル」「効く施策」の検証済み記述は、
**書いた時点で正しくても、時間が経つだけで偽になる**。この差を設計に持たないままKBを作ると、
検証が全部通り、被覆マップが埋まり、audit が黙ったまま、中身だけが静かに腐る。

だからこのKBでは鮮度を一級市民にする。仕組みは3つ。

## 1. `freshness` ブロック（trend 必須・stage: dead を除く）

```yaml
freshness:
  valid_as_of: "2026-08-10"   # 最後に実データで確認した日
  recheck_by: "2027-02-10"    # 再検証の期限
```

`recheck_by` は **stage が決める**。手で計算しない（`tools/kb.py` の `recheck_deadline` が唯一の
実装で、`new_entity.py --stage` が埋め、`build_graph.py` が食い違いを落とす）。

| stage | 再検証まで | 理由 |
|---|---|---|
| `emerging` | 1ヶ月 | 立ち上がりは数週間で消えるか化けるかが分かれる。いちばん速く腐る |
| `growing` | 3ヶ月 | 四半期の数字で方向が確かめられる |
| `peak` | 6ヶ月 | 主流化したものは急には動かないが、頂点は過ぎてから分かる |
| `declining` | 6ヶ月 | 死んだかどうかの確認。急がないが放置もしない |
| `dead` | なし | もう動かない。美術史と同じ「確定した過去」に合流する |

期限を**早める**のは自由（検証は「導出より遅い」だけを落とす）。次の四半期決算の直後に見たい、
規制の施行日の翌週に見たい、という知識があるなら早めておく。

## 2. 「いま」の決め方 — 生成物に時計を使わない

鮮度切れの判定には「いま」が要る。だが生成物（`data/`・被覆マップ）の中で実時刻を使うと、
**リポジトリに何も変更が無くても、日付が変わるだけで生成物が古くなり**、CI の「生成物が最新か」が
時差だけで落ちる。生成物は入力（entities）に対して決定的でなければならない。

だから既定の「いま」は **データの最新日**（全エンティティの `updated` の最大値）にする。

- エンティティを書き足す・更新するたびに「いま」が前へ進み、鮮度が再評価される
- 書き込みが無ければ「いま」は止まる——**KBを触らない期間は、鮮度切れの検出も止まる**

この停止は仕様の弱点なので、2つの逃げ道を用意してある。

```bash
python3 tools/audit.py --dry-run --now 2027-01-01   # 生きた時計で見る（書き込みなし・表示だけ）
python3 tools/audit.py --dry-run --now $(date +%F)  # 今日の目で見る
```

**KBに触る日は、最初に `--now $(date +%F)` で鮮度を見る**のを習慣にする（investigation-task.md の
「次に何を調べるか」が最優先に置いている）。定期実行（Routine 等）を仕込むなら、
`--now` 付き dry-run の出力を通知させるのがよい——生成物を書き換えずに済む。

## 3. 腐った記述の扱い — 引用の側で止める

鮮度切れは削除ではない。`recheck_by` を過ぎた記述は:

- `bundle.py` の出力に **⚠ 鮮度切れ** の警告が付く（気づかず引用するのを防ぐ）
- audit が「鮮度切れ」として最優先で指す
- 外に出す文章では**断定に使わない**（[for-other-personas.md](for-other-personas.md) の表）

再検証して数字が変わっていなければ `valid_as_of` を更新するだけでよい。**「確認したが変わって
いなかった」も1件の作業として価値がある**——それが無いと、正しい記述と確認していない記述の
区別が消える。

## evidence の `as_of` — 数字の鮮度は記述の鮮度と別に動く

`freshness` は**記述**の鮮度、evidence の `as_of` は**数字**の鮮度。2024年調査の数字を2026年に
確認しても、それは「2024年時点の数字を2026年に見た」のであって、数字が2026年のものになる
わけではない。だから evidence の各行に `as_of`（調査時点・データ時点）を必須にしている。
本文で数字を使うときも時点を添える（「2025年度調査では◯◯%」）。

## stage を動かすとき

再検証で数字が動いていたら stage を引き直す（判定表は investigation-task.md）。約束は2つ。

1. **stage を変えたら、理由を本文に追記する**（「2026-Q2 の◯◯調査で利用率が前年割れ。
   declining に変更」）。frontmatter の diff だけでは、後から読む自分が理由を辿れない
2. **dead にしたら `killed_by` を張る**（audit が要求する）。何が殺したか——規制か、代替か、
   飽和か——は、いま持っている他のトレンドの寿命を測る材料になる
