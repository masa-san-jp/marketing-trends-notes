# 他の人格（アイコたち）向けの入口

このKBの**使い手はアイコたち**と masa。マーケティング・トレンドの記述を発信や判断に使うときは、
まずここを読む。

**読むだけなら書き手に聞かなくていい。** 下の3つのコマンドで足りる。

## 1. まず被覆マップを見る（何が入っているか）

```bash
cat overviews/coverage.md
```

trend × カテゴリ × 開始年の表。**空欄は「まだ無い」**という意味なので、無いものを探して時間を
使わない。**鮮度切れの一覧もここに出る**——載っていること自体より、いつ確認されたかを見る。

## 2. 語で探す（IDを知らなくていい）

```bash
python3 tools/bundle.py --search ショート動画    # 触れているものの一覧
python3 tools/bundle.py --search リテールメディア # 該当なしなら「まだ無い」と返る
```

**探した語は記録されます**（`data/queries.jsonl`）。該当なしだった語は被覆マップに「探されたが
無かった語」として出て、次に何を埋めるかの判断材料になります。**空振りも無駄になりません**——
むしろ空振りの方が需要のシグナルとして効くので、遠慮せず探してください。

## 3. 知りたいものを1文書で取り出す

```bash
python3 tools/bundle.py trend/short-video-mainstream       # 1件＋周辺（応答する施策・チャネル・出典）
python3 tools/bundle.py --category entertainment-content   # カテゴリでまとめて
python3 tools/bundle.py trend/... -o /tmp/x.md              # ファイルへ
```

出力は markdown 1本。出典URLが末尾に集約される。**鮮度切れの節には ⚠ が付く**——付いていたら
その記述は断定に使わない。

## 引用するときの約束

このKBの記述は段階に分かれている。**外に出す文章で扱いを変えてください。**

| 印 | 意味 | 外に出すとき |
|---|---|---|
| `status: verified` | 利害のない根拠で裏が取れ、**かつ書き手が原典を1本は開いている** | 出典を添えて書ける |
| `status: draft` | 書いたが根拠が薄い | 「〜とされる」の形にする。断定しない |
| `status: stub` | 枠だけ | **引用しない** |
| **`recheck_by` 超過（⚠ 鮮度切れ）** | **書いた時点では正しかったが、いまは分からない** | **断定に使わない。** 使う前に再検証を頼む |
| `certainty: vendor` の数字 | その主張で儲かる側の数字 | 使うなら「◯◯社調べ」を必ず添える。規模の断定に使わない |
| `kind: vendor-pushed` の trend | 供給側が名付けて売り込んだ括り | 「流行っている」と書かない。「◯◯が提唱する」の形にする |
| 本文の `**未確認**:` の行 | 書き手が確かめられなかったこと | **事実として書かない** |
| `certainty: hypothesis` | 書き手の仮説 | 見立てとして書く。データと混ぜない |
| `retrieved: summary` の根拠 | **出典URLは付いているが、書き手は原典を開いていない** | その数字を引くなら**自分で原典を開いてから**。URLがあることは読んだ証拠にならない |

**このKBで特に注意が要るのは鮮度です。** 美術史と違って、verified でも `recheck_by` を過ぎていたら
もう正しくないかもしれない。**「verified だから断定できる」ではなく「verified かつ期限内だから
断定できる」**。bundle の ⚠ がその判定を代行します。

**「未確認」を落として断定文にするのが、いちばんやってはいけない加工です。**
2番目が、ベンダーの数字から「◯◯社調べ」を落とすこと。どちらも出典のない断定を作ります。

## 追加・訂正・再検証を頼むとき

**GitHub issue を立ててください**（`kb-request` ラベル）。書いてほしいのは3つ:
**用途**（何に使うか）・**期日**・**断定で使うか**（＝verified まで上げる／再検証する必要があるか）。

```bash
gh issue create --repo masa-san-jp/marketing-trends-notes --label kb-request \
  --title "<何を入れて/確かめてほしいか>" \
  --body "用途／いつまでに要るか／断定で使うか"
```

鮮度切れの記述を使いたいときも同じ形で。再検証は1件1タスクで回ります
（[investigation-task.md](investigation-task.md) の「鮮度の更新タスク」）。

## やってほしくないこと

- `entities/` を直接書き換える（スキーマ検証があるので壊れます。追加・修正は issue で）
- `data/` と `overviews/coverage.md` の生成ブロックを編集する（次の生成で消えます）
- 未確認・鮮度切れ・vendor の記述を断定に変えて外に出す（上の表のとおり）
